# X（Twitter）账号绑定联调台

> **权威源是后端仓的 `docs/contracts/x-import.md` 与
> `api/business/v1/ximport.proto`**（机器格式：`docs/contracts/x-import.openapi.json`）。
> 本文是 2026-08-31 的快照 + 本前端的用法，冲突一律以后端仓为准。

页面在 `http://13.52.177.63:7500/x`（回调页 `/x/callback` 是同一个视图）。
本机上 `http://localhost:7500/x` 是同一个东西 —— dev server 绑的是 0.0.0.0，
两个入口都通。**但只有走 localhost 才是浏览器眼里的「安全上下文」**，
见下面 §2 的注意事项。
顶部导航在它与登录联调台之间切换，**事件日志两边共用** —— 切走再切回来，
刚才那次失败的线索还在。

## 0. 前置：先有本站 JWT

四个 `/v1/user/x/*` 端点**全部是 Required 档**，没有 `Authorization: Bearer`
一律 `400000`。所以顺序是：

1. 在「登录联调台」走一遍 Privy 登录 → 「换取本站 token」
2. 再切到「X 账号绑定」

页面在没有 JWT 时不会发任何请求 —— 那一发必然 400000，只会在日志里留一条
误导人的失败。

## 1. 后端要配好什么

| 配置项 | 位置 | 不配会怎样 |
|---|---|---|
| `x.client_id` | `configs/business.yaml` | 四个端点显式回 `500097`（`metadata.upstream=x`） |
| `x.redirect_uri` | `configs/business.yaml` | 同上 |
| `x.client_secret` | `configs/business.secret.yaml` | X 后台把 App 建成 **public client（PKCE-only）时留空才是对的**，填了反而被 X 拒；建成 confidential client 时不填则换 token 一律 401 |
| `sorsa.api_keys` | `configs/business.secret.yaml` | **绑定与档案照常可用**，只是关注导入不启动 —— 表现为 `follow_import.status` 一直是 1，本页轮询 2 分钟后停 |

`500097` 与 `404` 是两回事，页面上也分得开：前者是**信封里的业务码**（路由在、
没配上游），后者是**裸 HTTP 404**（这个后端根本没有这条路由，是旧构建）。

## 2. redirect_uri：两条路，先确认走哪条

后端 `x.redirect_uri` 必须与 X 开发者后台（Settings → User authentication
settings → Callback URI / Redirect URL）登记的值**完全一致** —— 差一个斜杠、
差 http/https，X 都会拒绝授权码，而它只回一句 `invalid_request`，不告诉你哪里
不一致。

### 自动路径（理想情况）

两边都登记成**这台机器的公网地址**：

```
http://13.52.177.63:7500/x/callback
```

用户在 X 点确认后回到本页，页面自己从 URL query 读 `code` 与 `state` 并提交。
vite dev server 对无扩展名路径做 SPA 回退，`/x/callback` 会返回 index.html
（已实测），所以不需要任何额外的路由配置。

用公网 IP 而不是 `localhost`，是因为 **X 的回跳是从用户的浏览器发起的**，
而联调的人不在这台机器上 —— 写 `localhost` 的话，回跳会落到**他自己的**
127.0.0.1，那里什么都没有。这也顺带绕开了下面那条未证实的限制。

> ⚠️ **X 官方文档没有说明是否允许 `http://localhost` 作为 Callback URI，
> 这一点尚未实测。** 换成公网 IP 后这条不再挡路，但 **X 是否接受
> 「裸 IP + http」形态的 Callback URI 同样未实测** —— 有些 OAuth 提供方
> 只认域名、或强制 https。填进 X 后台时若被拒，直接走下面的手工兜底。

> ⚠️ **`http://` + 裸 IP 不是浏览器的「安全上下文」**：页面上的复制按钮会失效
> （已做显式提示，不会静默失败），Privy 那边依赖 `crypto.subtle` 的能力也
> 可能受影响。**先在本机 `http://localhost:7500` 上换到 JWT、确认登录链路正常，
> 再从公网入口测 X 绑定**，能省掉一整轮"到底是谁坏了"的排查。

### 手工兜底（任何配置下都能用）

redirect_uri 指向别处（甚至是一个 404 页面）时：用户点完授权后，
**地址栏里那串 `?code=…&state=…` 是完整的**，把**整个 URL** 粘进页面上
「回调 URL（手工兜底）」那个框，点「解析并提交绑定」即可。

框子四种形态都吃：完整 URL、带 `#` 的 URL、光一段 `?code=…&state=…`、
连问号都没有的 `code=…&state=…`。粘进来后会实时显示解析出的 code / state /
error，解析不出来当场就看得见。

## 3. 五步剧本

| 步骤 | 页面上做什么 | 期望 |
|---|---|---|
| 1 | 打开 `/x`，看「当前绑定状态」 | 没绑过 → `200106`，页面显示"未绑定"（**这是正常状态，不是错误**） |
| 2 | 点「发起绑定」 | 拿到 `authorize_url` + `state`，倒计时开始（state 只活 10 分钟） |
| 3 | 点「跳转到 X 授权页」，在 X 上点确认 | 回跳带 `code` + `state` |
| 4 | 自动提交，或把回调 URL 粘进兜底框 | 拿到 `bound=true` + X 档案，`follow_import.status=1` |
| 5 | 页面每 5 秒轮询一次 | `status` 变成 2/3/4 即停；2 分钟仍是 1 就停手并提示 |

跳转**故意用当前标签页**：`state` 存在本标签页的 sessionStorage 里，
新标签页读不到（那边跳回来会显示"没有发起中的绑定"，而人明明刚点过）。
真在新标签页里完成了授权也不算废 —— 手工兜底那条路仍然能把 URL 粘回来。

用户在 X 授权页点「取消」时，X 带 `error=access_denied` 回跳而**不带 code**，
页面识别它并给出人话提示，不调后端。

## 4. 四种导入状态，别混

`follow_import.status` 是 **JSON number 不是名字**（1/2/3/4）：

| status | 页面显示 | 说明 |
|---|---|---|
| 1 PENDING | 导入中 | 后台还没跑完（典型 30 秒内开始）。轮询 |
| 2 SYNCED | 已完成 | 用 `count` 显示条数 |
| 3 FAILED | 导入失败 | **不会再自动重试**；解绑后重绑可再试一次 |
| 4 PROTECTED | 账号受保护 | 抓取通道**拿不到**关注列表 |

**「SYNCED + count 缺席」（这个人确实没关注任何人）与「PROTECTED」
（拿不到）是两回事**，界面上必须分得开 —— 混成一句"0 个关注"会让受保护
账号看起来像导入成功了。

## 5. 两条编码事实（照 proto 手推一定会错）

回包经 Go 标准库 JSON 编码：

1. **零值字段整个缺席**。`count` 为 0、`truncated` 为 false、`synced_at` 为空
   时，这些 key 根本不出现。所以判断"没关注任何人"要写
   `status === 2 && !count` —— 写 `count === 0` 拿到的是 `undefined`，
   判断恒为 false，界面会一直显示"导入 undefined 条"而不报任何错。
2. **枚举编成数字不是名字**。当字符串比（`=== 'PENDING'`）同样不报错，
   只是永远不成立，症状是进度永远停在初始态。

页面把「缺席」当成一个**要显示的事实**打在界面上（`count=(缺席=0)`），
联调时最需要看见的就是"后端到底给没给这个字段"。

## 6. 码表与动作

| 码 | 含义 | 动作 |
|---|---|---|
| `100116` | code/state 缺失或格式非法 | 检查请求体，多半只解析出了半边 |
| `100117` | 授权码已用过或已过期 | **重新从第 2 步发起**，重试本请求无用 |
| `200106` | 没有生效的绑定 | **正常状态**，展示未绑定态 |
| `400103` | state 无效/过期/不属于本人 | **重新从第 2 步发起** |
| `420103` | 24 小时内绑定次数超限（滚动窗口） | 稍后再试，**不要自动重试** |
| `430108` | 本人已绑定 | 先解绑；同时刷新本地绑定态 |
| `430109` | 该 X 账号已被他人绑定 | 换账号或让原主解绑，**不要自动重试** |
| `500097` | 上游未配置/不可用 | 看 `metadata.upstream`（`x` / `database`） |
| `500105` | X 上游故障 | 可稍后重试 |
| `400000` | 未登录 | 去登录联调台换 token |
| `420000` | 限流 | 退避；轮询保持 5 秒节奏，别更密 |

**同一份 `{code, state}` 只能提交一次**，第二次回 `400103`（不是 `100117`）——
state 在第一次提交时就被消费掉了，连换 token 那步都走不到。所以页面在
**提交之后无论成败都清掉本地的 state**：留着的话按钮还亮着，而它已经注定失败，
症状是"我明明照文档做了却一直 400103"。

同理，页面在读到回调参数后**立刻洗掉地址栏**：留着的话，任何一次刷新都会重放
一份已经被消费的 code，而 `400103` 的说明是"重新发起"，与真实原因（你只是
刷新了一下）完全对不上。参数已存进 sessionStorage 并填进手工框，不会丢。

## 7. 已知状态（2026-08-31 实测）

- **测试服 `http://13.231.246.26:8080` 上还没有这四条路由**：
  `GET /v1/user/x/binding` 回**裸 HTTP 404**，而同一台机器上
  `POST /v1/auth/login` 回的是正常信封（`400100`）—— 说明那台是 X 绑定合并
  之前的构建。页面会把这件事直接说出来，不用去查鉴权或代理。
- **后端 `configs/business.yaml` 的 `x.redirect_uri` 当前留空**，
  即便换上带 X 路由的构建，不填这一项四个端点也只会回 `500097`。
- 本页存的两条临时记录都在 **sessionStorage**（不是 localStorage）：
  `smartx-login-fe.x_bind_pending`（发起时的 state）与
  `smartx-login-fe.x_callback`（抓到但还没提交的 code）。
  它们只对当前标签页的这一次绑定有意义，跨浏览器重启活下来只会制造
  "一个早就作废的 state 还在页面上"。
